# FGAI-2026-001 — System Architecture Recommendation (v0.1)

Status: **DRAFT — awaiting ARCH gate (Tech Lead + Security).**

## 1. Recommendation (one paragraph)
A **TypeScript pnpm monorepo** made of a **Next.js 15 (App Router) PWA** for every role's UI, a separate **Fastify API** with a generated **OpenAPI 3.1** contract, **PostgreSQL 17** reached through **Drizzle ORM**, and a **Postgres-backed job queue (pg-boss)** for notifications. All of it runs with one `docker compose up`. Provider-abstracted packages handle AI (`packages/ai`) and payments (`packages/payments`), and in the MVP each ships only a deterministic or sandbox implementation.

## 2. Key decisions and trade-offs (ADR summaries)

| ADR | Decision | Alternatives considered | Why |
|---|---|---|---|
| 001 | Separate Fastify API (not only Next.js route handlers) | Next.js-only full stack; NestJS | One place for authorisation; reusable by a future Expo app; OpenAPI is easy to generate. NestJS is heavier than an MVP needs |
| 002 | PostgreSQL + Drizzle | Prisma; Supabase | Drizzle gives SQL-transparent migrations and easy row-level patterns. Supabase brings an external account and its auth model too early |
| 003 | pg-boss queue in Postgres | Redis + BullMQ; cloud queue | One fewer service, transactional enqueue (alert and job commit together), retries and dead-letter built in. Swap in BullMQ if throughput demands it |
| 004 | First-party auth behind an `AuthProvider` interface | Auth0 / Clerk / Keycloak now | No external credentials for the demo. Argon2id + DB sessions are well understood. Migrate to a managed IdP (with MFA and passkeys) in P1 |
| 005 | Authorisation = RBAC + relationship + **ConsentGrant** (ABAC) in one `policy.ts` | Postgres RLS only | Easier to unit-test across the matrix. Postgres RLS added later as defence in depth |
| 006 | ScamShield = rules engine first, optional LLM explainer | LLM-only classifier | Deterministic, testable, works offline. LLM output is constrained (it can raise risk, never lower it). Versioned prompts and an eval set live in `packages/ai/evals` |
| 007 | Web PWA first; Expo in P2 | Expo now | Shorter path to a demo. App-store IAP rules only apply once there is a native app |
| 008 | Simulated notification and payment adapters | Real FCM / email / gateway | No external sends or charges without approval. Adapters write the same state machine, so real providers drop in later |

Optional AI provider (if B2 = yes): Anthropic API, `claude-haiku-5-5` for low-cost explanation (escalate to `claude-sonnet-5-5` if the eval quality needs it), dev key only, synthetic data only.

## 4. Core flows
**Notification engine:** `Signal` (help request, scam check shared, missed reminder [P1]) → `RuleEvaluation` (severity, target purpose) → `ConsentCheck` (active grant for recipient × category) → `Alert` + `Notification` rows (state `queued`) → worker delivers via adapter → `sent | failed(retry n/3, backoff)` → recipient `seen` → `acknowledged` → if no ack in T minutes, `follow_up` to next permitted contact. A notification is never created for a recipient without a grant, and the check runs again at delivery time (so a revoke between queue and send stops the notification).

**Alert severity labels** distinguish `system_warning` (generated by app rules) from `user_requested_help` (the senior pressed Help). "Verified emergency" does not exist in the MVP because nothing is verified by an agency.

## 5. Entities: authorisation and retention

| Entity | Who can read | Who can write | Retention (proposed) |
|---|---|---|---|
| Users | self; admin (profile metadata only) | self; admin (status only) | Account lifetime + 30 days after deletion request |
| Families / FamilyMemberships | members (names, relationship) | senior (owner) | Lifetime of the family; removal = immediate |
| ConsentGrants | senior; grantee (their own grants) | **senior only** | Expired/revoked grants kept 2 years for audit (metadata only) |
| TrustedContacts | senior; members with "contacts" grant | senior | Until removed |
| WellbeingCheckins | senior; grantee with `checkins` grant (note only if the senior marked it shareable) | senior | 12 months rolling, then purged; export available |
| HealthReminders / CareTasks (P1) | senior; grantees with `care` grant | senior; caregiver (completion only) | 12 months after completion |
| ScamAssessments | senior; grantees with `scam` grant | senior | Raw text 30 days, then only risk category and signals kept 12 months |
| GuardianPauseSessions | senior; grantees with `transfer_pause` grant | senior | 90 days |
| Alerts / Notifications | recipient + senior | system | 12 months; content stripped on revoke |
| CaseSummaries | senior; recipients the senior chose | senior | Until deleted by the senior; marked "prepared by user — not submitted to any agency" |
| PartnerDirectory | everyone | admin (audited) | Versioned forever |
| Subscriptions / PaymentTransactions (sandbox) | payer; admin (billing metadata) | system via verified webhook | As required by tax law for real payments (to confirm); sandbox data purgeable |
| AuditEvents | senior (events about them); admin (operations) | system, append-only | 2 years |

## 6. Payments architecture (P1, sandbox)
`Plan` → `Entitlement` (features per family) is kept separate from `PaymentProvider` (adapter: `createCheckout`, `verifyWebhook`, `refund`). Webhooks are verified by HMAC and are idempotent on `provider_event_id`. Subscription states: `trialing → active → past_due → canceled | refunded`. No card data touches our servers (hosted checkout only, even in the future). Live providers are disabled unless `PAYMENTS_LIVE=true` **and** credentials exist **and** a release flag has been signed.

## 7. Environments
`local` (Docker), `staging` (TBD, B6), `production` (not in scope). Secrets come only from env vars and a secrets manager; `.env` is git-ignored and `.env.example` holds placeholders. Observability: structured JSON logs with redaction, health endpoint, and queue metrics on the admin page.
